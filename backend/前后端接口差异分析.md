# 前后端联调 · 差异分析报告（第一步）

> 分析对象：队友前端《API接口文档(2).md》+《数据库表结构文档(2).md》+ GitHub 仓库 `anker147/Hiu-2026-Message-Board-Frontend`（已克隆核对 Mock 源码）
> 我方后端：TestJDBC（JSP/Servlet/JDBC，Tomcat 6 + Servlet 2.5 + JDK 1.7 + MySQL 5.5）
> 结论一句话：**前端契约是"REST 风格 JSON API + Bearer Token 认证"，我方后端是"表单时代 Servlet + Session Cookie 认证"，差异是体系级的，不是改几个参数名就能对上的。** 但对齐路径清晰，详见文末方案。

---

## 一、五大体系级差异

### 1. 请求路径（URL）——完全不同

| 功能 | 前端要求 | 我后端现状 |
|---|---|---|
| 注册 | `POST /api/register` | `POST /TestJDBC/RegisterServlet` |
| 登录 | `POST /api/login` | `POST /TestJDBC/LoginServlet` |
| 退出 | `POST /api/logout` | `GET /TestJDBC/LogoutServlet` |
| 留言列表 | `GET /api/messages?tab=&period=&q=` | `GET /TestJDBC/QueryMessageServlet`（返回整个 HTML 页面，不是 JSON） |
| 发布留言 | `POST /api/messages` | `POST /TestJDBC/AddMessageServlet` |
| 发评论 | `POST /api/comments` | `POST /TestJDBC/AddCommentServlet` |
| 发回复 | `POST /api/replies` | 同上（用 parent_id 区分） |
| 编辑内容 | `PUT /api/content/{resourceId}` | `POST /TestJDBC/UpdateMessageServlet` / `UpdateCommentServlet` |
| 删除内容 | `DELETE /api/content/{resourceId}` | `GET /TestJDBC/DeleteMessageServlet?id=` / `DeleteCommentServlet?id=` |
| 个人中心 | `GET /api/profile` | 无此接口 |
| 评论树 | `GET /api/messages/{id}/comments` | 无独立接口（评论嵌在列表 HTML 里） |
| 点赞 | `POST /api/like` | `POST /TestJDBC/LikeServlet` / `LikeCommentServlet`（两个接口） |
| 盲盒 | `GET /api/blindbox` | `GET /TestJDBC/RandomMessageServlet` |
| 盲盒匿名回复 | `POST /api/blindbox/reply` | 复用 `AddCommentServlet`（非匿名） |
| 会话查询 | `GET /api/session` | 无 |
| 个人主页 | `GET /api/zone?displayId=` | 无 |
| 隐私开关 | `PUT /api/profile/privacy` | 无独立接口（藏在发留言表单里） |
| 昵称/签名/头像 | `PUT /api/profile/nickname` | `UpdateAvatarServlet`（仅头像） |
| 敏感信息编辑 | `PUT /api/profile/sensitive` | 无 |
| GM 管理 | `/api/gm/*` 共 17 条路由 | **完全没有** |

前端还用了**路径参数**（`/api/messages/{resourceId}`）——Servlet 2.5 没有 `@PathVariable`，需要在 Servlet 里手写 `getPathInfo()` 解析。

### 2. 请求方法——前端要求 PUT / DELETE

前端大量使用 `PUT`、`DELETE`（编辑、删除、隐私开关、GM 处置）。我后端所有 Servlet 只有 `doGet→doPost`。Tomcat 6 支持 `doPut/doDelete`，需要重写。

### 3. 响应格式——前端要求统一响应包 + 固定错误码

前端硬性要求**所有接口**返回：

```json
{ "success": true, "code": 0, "message": "ok", "data": { } }
```

失败时 `code` 必须是文档 §0.3 的固定错误码（1001/1002/1003/1009/2001/2002/2003/4001/4002/5001/5002/5003/6001~6006/9001/9002/9003/401），**前端只看 code 做逻辑分支**。

我后端现状：各 Servlet 手拼的零散 JSON（`{success,liked,count}`、`{success,type,id,message_id}`……），**没有 code 字段、没有统一 data 包装**；大部分接口干脆返回 HTML 页面或 302 重定向。

### 4. 鉴权体系——前端是 Bearer Token + CSRF，我后端是 Session Cookie

| 项 | 前端要求 | 我后端现状 |
|---|---|---|
| 会话载体 | `Authorization: Bearer <48位token>` 请求头 | `HttpSession` + JSESSIONID Cookie |
| 会话存储 | `sessions` 表（token/userId/csrf/lastActive） | 内存 Session |
| 超时 | 空闲 30 分钟 → 401 | 无超时控制 |
| 写操作 | 必须带 `csrf` 参数且与会话一致，否则 9002 | **无 CSRF** |
| 登录保护 | 连续失败 5 次锁 15 分钟（2002） | 无 |
| 登出 | Token 立即失效，重放 401 | session.invalidate() |

**关键点：跨域场景下 JSESSIONID Cookie 受 SameSite 限制基本不可用，必须改为 Token 方案**（文档 §0.2 也写了"真实后端用 Header/Cookie 均可"，但独立前端 + CorsFilter 场景下只有 Token 靠谱）。

### 5. 参数名——几乎全部不同（重点核对表）

| 功能 | 前端参数名 | 我后端参数名 |
|---|---|---|
| 注册 | `phone`, `password`, `name`(真实姓名), `email` | `account`, `password`, `user_no`, `avatar`, `email`, `confirm` |
| 登录 | `phone`, `password` | `account`, `password` |
| 发留言 | `title`, `content`, `nickname`, `topic`, `csrf` | `nickname`, `real_name`, `email`, `phone`, `content`, `is_name_public`, `is_email_public`, `is_phone_public` |
| 发评论 | `messageId`, `content`, `nickname`, `csrf` | `message_id`, `parent_id`, `content` |
| 发回复 | `messageId`, `commentId`, `content`, `atDisplayId`, `nickname`, `csrf` | `message_id`, `parent_id`, `content` |
| 点赞 | `targetId`, `idemKey`(幂等键), `op`(like/unlike), `csrf` | `message_id` 或 `comment_id` |
| 编辑 | `content`, `title`, `topic`, `isPublic`, `csrf` | `id`, `content`, `nickname`, `real_name`, `email`, `phone`, `is_xxx_public` |
| 删除 | `csrf`（id 在路径） | `id` |
| 盲盒回复 | `messageId`, `content`, `csrf` | `message_id`, `parent_id=0`, `content` |
| 隐私开关 | `flagName`, `flagEmail`, `flagPhone`, `flagLiked`, `flagFavorite` | `is_name_public` 等（随留言提交） |

**ID 类型也不同**：前端的 `messageId/commentId/targetId` 全是 UUID 字符串（`"u1x2y3-..."`），我后端是 int 自增主键。返回字段名是 `resourceId`，不是 `id`。

## 二、数据库差异（表结构对照）

| 前端要求（文档 §0.1，共 11 张表） | 我后端现状（5 张表） | 差异要点 |
|---|---|---|
| `users`（display_id 8位数字、avatar_enum 1~8、role/status/mute_until、flag_name…、password 哈希） | `mb_user`（user_no 8位hex、avatar "av1"字符串、明文密码） | 字段名、ID 规则、头像格式全不同；缺 role/status/mute/bio |
| `messages`（resource_id UUID 主键、no、title、topic_tag、is_public、period、stats 四列、heat_delta、peak_rank、is_new、edited、nickname_snapshot、avatar_url、images、cover_url、hidden） | `mb_message`（int 主键、nickname、real_name、email、phone、is_xxx_public、content、status） | 主键类型不同；缺标题/话题/期次/统计列/隐藏标记；`status` vs `is_public` 语义不同 |
| `comments`（resource_id、depth 1~2、root_id、at_display_id、is_anonymous、likes 计数列、edited） | `mb_comment`（parent_id 两级树） | 结构可映射：parent_id→parentId，但缺 depth/rootId/匿名标记/编辑标记 |
| `likes`（多态：user_id + target_id + target_type，幂等唯一约束） | `mb_like` + `mb_comment_like`（两张表） | 前端一张表统一帖子/评论点赞，还要求 idemKey 幂等 |
| `sessions` / `login_fails` / `rate_window` / `settings` / `meta` / `blindbox_replies` | **完全没有** | Token 会话、登录锁定、限流滑窗、全局配置、盲盒匿名审计 |
| `admin_actions`（GM 审计，只增不删） | **完全没有** | GM 模块依赖 |
| 收藏 `favorites` | **完全没有**（前端 api.js 有 favorite 接口） | 文档表清单也漏了这张表（见第五节） |

**时间戳单位**：前端全部要求毫秒数（`createdAt: 1730000000000`），我后端是 DATETIME。
**密码存储**：文档红线要求 PBKDF2/bcrypt 加盐哈希，我后端明文。
**富文本**：`content` 允许白名单 HTML 片段（§0.6），字数与敏感词按去标签后的可见文字计算——我后端按纯文本处理。

## 三、安全与业务规则差异

| 规则 | 前端要求 | 我后端现状 |
|---|---|---|
| 敏感词 | 词表只有 4 词（加微信/代考/办证/刷单），且要可配置（settings 表） | SafetyFilter 硬编码 9 词，覆盖留言/评论/回复 |
| 限流 | **仅发留言**：同账号 10 秒滑窗 >3 次 → 4002 + 剩余秒数 | 10 秒内 >1 次就拦（比前端严） |
| 匿名红线 | 盲盒回复输出层永远"热心同学"，真实身份只进审计表 | 盲盒回复非匿名，直接显示网名 |
| 点赞幂等 | `idemKey` 重复请求返回当前状态不抖动 | 无幂等键 |
| 脱敏 | 列表接口只回掩码，明文唯一出口 `GET /api/profile`；掩码受 flagXxx 开关控制（关=空串） | 掩码在留言行内，随留言的 is_xxx_public |
| owner 校验 | 5002 错误码 | 有（文字提示） |
| 评论层级 | 最多两级，超限 5003 | 有（内存拼树） |

## 四、跨域问题（第三步预告）

- 前端联调方式：`python -m http.server 8080`（或 GitHub Pages），与我方 Tomcat **不同源** → 必须新增 `CorsFilter`：
  - 响应头 `Access-Control-Allow-Origin: *`（或联调白名单）、`Allow-Methods: GET,POST,PUT,DELETE,OPTIONS`、`Allow-Headers: Content-Type,Authorization`；
  - 放行 `OPTIONS` 预检请求（PUT/DELETE + 自定义头必然触发预检，**Servlet 2.5 下 OPTIONS 默认 405/405 会被预检卡死**，必须在 Filter 里直接短路返回 200）；
  - 注意端口：前端文档写的联调端口 8080 与 Tomcat 8080 冲突，建议前端用 8081，或前端静态页直接丢进 TestJDBC webapps 同源部署。
- **请求体格式未在文档约定**（JSON 还是 form）：Mock 层是函数调用，没写 Content-Type。建议后端两种都兼容（form-urlencoded + JSON body 手写解析），联调时 whichever 都通。

## 五、前端已实现、但两份文档没写全的（第四步补文档素材）

对照仓库 Mock 源码（`js/mock/api.js` 1853 行）发现文档遗漏：

1. **`favorite` 收藏接口**（帖子 + 评论，幂等，`{targetId, idemKey, op, csrf}` → `{favorite, count}`）——接口清单完全没有；
2. `toListMessage` 实际还返回：`avatarUrl`、`images[]`（最多 10 张）、`coverUrl`、`coverFromFirst`、`weeklyStats[]`、`hidden`、`hiddenReason`；
3. `postMessage` 实际还接收：`images`、`coverUrl`、`coverFromFirst` 参数；
4. `getProfile` 实际还返回：`avatarUrl`、`flagLiked`、`flagFavorite`；
5. `updatePrivacy` 实际还接收：`flagLiked`、`flagFavorite`（互动展示开关）；
6. `updateNickname` 实际还接收：`avatarUrl`（`localimg://id` 引用，空串回退 emoji）；
7. `getMessage`（详情）实际还返回：`isMine`、`isLiked`、`isFavorite`；
8. 评论对象实际还返回：`favorites`、`isLiked`、`isFavorite`、`hidden`、`hiddenReason`；
9. **图片机制**：图片存在前端 localStorage（`localimg://id` 引用），**后端只需存引用字符串，不需要做文件上传**——这大幅降低第二步工作量；
10. 表结构文档缺 `favorites` 表（或 likes 表的 favorite 语义扩展）。

## 六、建议实施方案（待你确认后执行）

**总体策略：不动你现有的 JSP 前台和 17 个旧 Servlet（答辩演示保留），在同一个项目里新增一层 `/api/*` REST 接口。**

1. 新增 `util.ApiResp`（统一响应包 + 错误码常量 + 手写 JSON 输出）；
2. 新增 `util.TokenAuth`（从 `Authorization: Bearer` 头解析会话：查 sessions 表、30 分钟空闲、CSRF 比对、顺延 lastActive）；
3. 新增约 15~20 个 `Api*Servlet`（`/api/register`、`/api/login`、`/api/messages`、`/api/comments`、`/api/replies`、`/api/content/*`、`/api/profile/*`、`/api/like`、`/api/blindbox`、`/api/session`、`/api/zone`……），请求体兼容 form 与 JSON；
4. 数据库按文档新建 11 张表（`users/messages/comments/likes/sessions/...`），旧 `mb_*` 表原样保留互不干扰；密码按红线做 PBKDF2（JDK 1.7 自带 `Pbkdf2WithHmacSHA1`，零依赖可行）；
5. 新增 `filter.CorsFilter`（含 OPTIONS 预检短路）+ web.xml 注册；
6. 编译（ecj，Java 7 字节码）→ 临时 Tomcat + curl 逐接口验证 → 补全两份 MD 文档。

- C. 要不要我顺手写一份**前端 fetch 适配层**（替换 `js/mock/api.js` 的 `js/api.js`，含 baseURL 配置），让你队友直接拿去联调？
